# T10 · Sealed list: the Safe, the teller-window module and the Merkle root

**In one sentence.** A real Safe holds the funds. The asset manager ticks protocols, and the platform turns them into a list of allowed operations sealed by a Merkle root. The manager signs that root: for now, the manager's signature alone is enough (Safe 1 of 1). A Safe module, the teller window, runs an operation only if it proves membership in the root. The agent, which has no key, cannot act outside the list, even when it is manipulated.

**Why now.** "Allowed is not safe" needs an allowed perimeter that actually exists on-chain. This task brings forward the sealed-list part of phase 2 (`TASKS.md` §5). It does it as an isolated track: TreasuryVault, the scenario and the monitoring (T1–T5) are not touched.

## Architecture

```
Agent (stub, NO key) ── proposal (data) ──► Platform "teller" (OPERATOR key)
  {deposit, lend-avax, USDC, 100k}            calldata → leaf → Merkle proof
                                              not in the list → refused, no transaction
                                                  │ module.execute(target, data, pinMask, proof)
Asset manager ── SafeTx signed (EIP-712) ─┐       ▼
 (1 signature)   enableModule / setRoot   └─► SealedListModule (teller window)
                                              root = the seal, settable ONLY by the Safe
                                              recomputes the root; lands elsewhere ⇒ revert
                                                  │ execTransactionFromModule (CALL, value 0)
                                                  ▼
                                            Safe 1.4.1 (canonical on Fuji) ── USDC ──► lend-avax / lend-eth
```

- **Contract** `contracts/src/SealedListModule.sol`:
  - `setRoot` and `setOperator` can be called only by the Safe, so only with the asset manager's signature;
  - `execute` can be called only by the operator; it runs a CALL only, with value 0;
  - the Safe itself and the module are never valid targets.
  - A refusal reverts with `NotInSealedList(leaf, computedRoot, sealedRoot)`.
  - Same principle as Veda BoringVault's `ManagerWithMerkleVerification`, without per-protocol decoders.
- **Leaf** (one allowed operation): `keccak256(keccak256(abi.encode(target, selector, words, pinMask, keccak256(pinned words))))`. Bit *i* of `pinMask` pins argument word *i*.
  - The tooling rule: every address argument is pinned and amounts stay free.
  - Merkle pairs are hashed sorted (OpenZeppelin `MerkleProof`), leaves are sorted, and an odd node is carried up unchanged.
- **What ticking one protocol adds:** three operations.

| Operation | Call | Pinned | Free |
|---|---|---|---|
| Approve | `USDC.approve` | spender = the market | amount |
| Deposit | `market.supply` | asset = USDC, onBehalfOf = the Safe | amount |
| Withdraw | `market.withdraw` | asset = USDC, to = the Safe | amount |

  The recipient is always the Safe. Even with a leaked operator key, funds can only move between the Safe and a ticked market.

## Keys

| Role | Local (anvil) | Fuji (`.env`, never committed) | Can do |
|---|---|---|---|
| Asset manager (front door, the Safe's only owner) | anvil account 10 | `SAFE_OWNER_PKS` (one key, no AVAX needed: it only signs) | sign Safe transactions: enable the module, seal a root |
| Operator (teller window) | anvil account 9 | `OPERATOR_PK` (topped up automatically by the deployer) | `SealedListModule.execute` only |
| Relayer | deployer | `DEPLOYER_PK` | pays gas; has no right on the Safe |
| Agent | none | none | proposes data |

For now the asset manager signs alone: Safe 1 of 1, `SAFE_THRESHOLD` = 1. Going back to a multisig, such as the brief's 3 of 5, is configuration only: several keys in `SAFE_OWNER_PKS` and a higher `SAFE_THRESHOLD`, then `make seal-deploy FORCE=1`.

## Commands

```bash
make seal-deploy                    # Safe owned by the asset manager + module, enabled by the manager; mints 1M test USDC to the Safe
make seal PROTOCOLS=lend-avax       # the asset manager signs the root of the list (lend-avax,lend-eth for both)
make seal-show                      # print the list, rebuild the root, compare with the module
make seal-demo                      # the full story below (NO_FORCE=1 skips the on-chain refusals)
make test-t10                       # Foundry (real Safe 1.4.1) + pytest (list + end to end on anvil)
python -m sealed.tree sealed/deployments/fuji.json   # anyone can rebuild the published root
```

`NETWORK` comes from `.env` or the command line. The USDC and market addresses come from `deployments/<network>.json` (T1). The T10 addresses, the published list and the sealing transactions are in `sealed/deployments/<network>.json`. It belongs to whoever connected last, so it is not committed (`sealed/.gitignore`); anyone can still rebuild its root with `python -m sealed.tree`.

Local runs need anvil and `make deploy`. The demo uses its own Safe; the markets are shared, and the demo withdraws everything at the end, so the reserves end as they started. If the T1 contracts are redeployed on Fuji, run `make seal-deploy FORCE=1` and then `make seal`.

## Dashboard flow (setup page, `make live` + `make frontend`)

1. **Connect your Safe.** The asset manager connects a browser wallet (Rabby, testnets on). The platform creates a Safe 1.4.1 owned by that address alone, deploys its `SealedListModule`, and credits test tokens (1,000,000 USDC and 500 WETH, minted by the deployer). The manager signs one SafeTx in the wallet (EIP-712): enable the module. The platform checks the signer and relays (`POST /api/safe/prepare`, `/api/safe/submit`); it pays the gas and never holds the manager's key.
2. **Choose your protocols.** Integrations are protocol × asset (`lend-eth:WETH`, `lend-avax:USDC`, …). Ticking one adds approve, deposit and withdraw-to-the-Safe. The manager signs the root in the wallet.
3. **Allocate.** Deposit or withdraw an amount through the teller window (`POST /api/safe/allocate`): real transactions on Fuji, refused off-chain when outside the list.
4. **Monitor.** Once a Safe is connected and exists on the chain, the T3 collector watches the Safe instead of TreasuryVault (`backend/collector.py`, `treasury_wallet`). Allocate WETH on lend-eth and launch the attack: the Safe is caught.
5. **Reset.** "Reset the test network" redeploys T1 and credits the Safe again on the new tokens; the list points at the old markets, so the dashboard asks the manager to seal it again (one signature).

`make seal-deploy` and `make seal` stay available for a server-side owner key (`SAFE_OWNER_PKS`), e.g. for tests and the CLI demo.

## Demo story (`make seal-demo`)

1. **Seal.** The asset manager ticks lend-avax: 3 operations, and the manager signs the root.
2. **Accepted.** The agent proposes "deposit 100,000 USDC on lend-avax" and "withdraw 40,000 USDC". Both run, and their links are printed.
3. **Refused by the platform, with no transaction:**
   - "transfer 500,000 USDC to 0x9c…f1" (poisoned document, the brief's example);
   - "withdraw 60,000 USDC to 0x9c…f1" (right function, wrong recipient);
   - "deposit on an audited protocol at 25%" (forum post, protocol not in the list);
   - "deposit on lend-eth" (not ticked).
4. **Refused on-chain.** Each refusal is replayed as a compromised platform would do it: the call is forced through the module with the proof of a real operation. The module recomputes a different root and reverts on-chain, with no effect beyond the network fee.
5. **Re-seal.** The asset manager ticks lend-eth: a new root and a new signature. The lend-eth deposit now runs.
6. **Exit.** Everything is withdrawn back to the Safe.

Every decision, refusals included, is appended to `data/runtime/<network>/sealed_decisions.jsonl`.

## Tests

- **Foundry** (`contracts/test/SealedListModule.t.sol`, 12 tests, real Safe 1.4.1 owned by the asset manager):
  - sealed deposit and withdraw pass;
  - transfer to an unknown address, withdraw to another recipient, and an unticked protocol are refused;
  - nothing passes before sealing;
  - a protocol revert undoes the call;
  - only the operator executes;
  - only the Safe sets the root or the operator;
  - a signature from anyone but the asset manager cannot seal (GS026);
  - re-sealing adds a protocol;
  - the Safe and the module are never targets, even when sealed.
- **pytest** (`backend/tests/test_t10_sealed.py`):
  - list tests that run everywhere: pinning, proofs for 1 to 8 leaves, order and duplicates, forged leaves, a published-list check;
  - chain tests on anvil: the Python leaf equals the module leaf, the full story, and only a Safe transaction signed by the manager changes the seal.

## Boundary check (`.agents/skills/boundary-check`)

| Question | Answer |
|---|---|
| Who proposes | the agent (data only) |
| Who verifies | the platform (off-chain list lookup), then the module (Merkle proof against the root signed by the asset manager) |
| Who executes | the Safe, through `execTransactionFromModule`, CALL only |
| Which key, and what it cannot open | the operator key can only call `execute`; it cannot change the root or the operator, cannot call the Safe or the module, cannot send native value, cannot choose a recipient other than the Safe |
| Can free text change a right | no: the root changes only through a Safe transaction signed by the asset manager |
| Does a refusal have a side effect | no: refused off-chain without a transaction, or reverted on-chain (network fee only) |
| Can a secret leak | keys are read from `.env` or derived from anvil's public mnemonic; only addresses are printed or written |

## Limits (v1)

- No caps yet (40% per protocol, human approval above $100,000). The brief puts them on the platform side, before each operation.
- No "facts re-read" gate yet. The bait (demo step 7) is in the list and must be blocked by the platform reading T3's risk state before it submits.
- Static-argument functions only (each argument is one 32-byte word). Real Aave v3 `supply` has an extra `referralCode` argument, which is one more free word.
- The circuit breaker is still TreasuryVault (T4). Next: a guardian module on this Safe (pause flag plus withdraw-to-Safe-only leaves).
- Decisions are logged locally and not yet anchored in `EvidenceRegistry`.
